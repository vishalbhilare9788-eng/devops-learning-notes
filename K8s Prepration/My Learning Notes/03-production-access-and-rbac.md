## The real question: how do people access K8s in production?
While learning, we SSH straight into the `master` node and run `kubectl` there. **That is not how
production works.** In production you almost never get direct SSH access to a manager/control-plane
node. Instead:

- You get access to a **jump/bastion host** — a regular machine with a full OS that has network
  **connectivity** to the master.
- `kubectl` is installed on that jump host (not the app logic — just the CLI).
- You get a **kubeconfig file** *from* the cluster (generated by whoever administers it) and put it
  in your own `~/.kube/config` on the jump host.
- From then on, `kubectl` on the jump host talks to the cluster remotely — you never log into the
  master directly.

### The 4 steps to get `kubectl` access from any new host
1. Confirm **network connectivity** between the host and the cluster's API server.
2. **Install `kubectl`** on that host (e.g. `sudo snap install kubectl --classic`).
3. Get the **config file** from the cluster admin.
4. Create `~/.kube/` on your host and copy the config file in as `~/.kube/config`.

```bash
alok@gitserver:~$ #connectivity - ok
alok@gitserver:~$ #install kubectl - ok
alok@gitserver:~$ #get config file - ok
alok@gitserver:~$ #copy config ~/.kube
```

**What's inside the config file:** the cluster's certificate, the master server's IP/address, the
cluster's name, and the username used to authenticate — that's the full picture of "who you are"
and "where the cluster is."

## Multi-tenant reality: namespace-scoped access
A production cluster usually has multiple namespaces (e.g. `dev`, `test`, `prod`), and different
users/teams should only access *their* namespace — not the whole cluster. This is where **RBAC**
(Role-Based Access Control) comes in.

> **Bonus (mentioned, not hands-on):** real production clusters usually plug into an existing
> directory service — **LDAP / Active Directory** — rather than creating individual Kubernetes
> users for every one of possibly thousands of employees. The cert-based flow below is what you'd
> use for a smaller/manual setup, or to understand the mechanics AD-integration builds on top of.

## RBAC = a 2-step process
1. **Create a `Role` (namespace-scoped) or `ClusterRole` (cluster-wide).**
   - `Role` → e.g. "Alok can create pods in the `prod` namespace only."
   - `ClusterRole` → e.g. "Alok can create pods in *any* namespace."
2. **Attach it to the user** (a `RoleBinding` or `ClusterRoleBinding`).

That's the whole model — everything below is just the mechanics of steps 1 and 2, plus how a user
identity gets created in the first place.

## Creating a certificate-based user ("ballu") end to end

### Step 1 — user generates a private key + CSR on their own workstation
```bash
openssl genrsa -out ballu.key 2048
openssl req -new -key ballu.key -out ballu.csr -subj "/CN=ballu"
```
`.csr` = Certificate Signing Request — "here's who I claim to be, please sign it."

### Step 2 — user sends the `.csr` to the cluster admin (root CA)
```bash
scp ballu.csr alok@10.0.0.100:
scp ballu.key alok@10.0.0.100:
```
*(Note: only the `.csr` — the public request — strictly needs to go to the admin; the `.key` stays
private to the user in a real-world flow. Both were copied here for the lab.)*

### Step 3 — admin signs the CSR using the cluster's own CA
```bash
openssl x509 -req -in ballu.csr \
  -CA /etc/kubernetes/pki/ca.crt -CAkey /etc/kubernetes/pki/ca.key \
  -CAcreateserial -out ballu.crt -days 365
```
This produces `ballu.crt` — signed by the **same CA the cluster itself trusts**, which is exactly
why Kubernetes will accept this certificate as a valid identity later.

```
root@manager:~# ll ballu.*
-rw-r--r-- 1 root root  981 ballu.crt
-rw-r--r-- 1 root root  875 ballu.csr
-rw------- 1 root root 1651 ballu.key
```

### Step 4 — admin registers the user + binds them to a namespace context
```bash
kubectl config set-credentials ballu --client-certificate=ballu.crt --client-key=ballu.key
# User "ballu" set.

kubectl config set-context ballu-context --cluster=kubernetes --namespace=prod --user=ballu
```
`set-credentials` creates the **identity** (who ballu is, proven by cert+key). `set-context` binds
that identity to a **specific cluster + namespace pairing** — this is what scopes ballu to `prod`
specifically, not the whole cluster.

## Writing the Role and RoleBinding YAML

Use `kubectl api-resources` to see what resources exist and can be referenced in a Role's rules.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: prod
  name: pod-creator
rules:
- apiGroups: [""]   # "" indicates the core API group
  resources: ["pods"]
  verbs: ["get", "watch", "list", "create"]
```
Later extended to cover more resource types in one Role:
```yaml
rules:
- apiGroups: ["", "apps/v1"]
  resources: ["pods", "deployments", "replicasets"]
  verbs: ["get", "watch", "list", "create"]
```

```bash
kubectl create -f prod-role.yaml
# role.rbac.authorization.k8s.io/pod-creator created

kubectl -n prod get roles
# NAME          CREATED AT
# pod-creator   2023-10-07T12:17:57Z
```

Now bind that Role to `ballu`:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: create-pods
  namespace: prod
subjects:
- kind: User
  name: ballu        # "name" is case sensitive
  namespace: prod
roleRef:
  kind: Role          # this must be Role or ClusterRole
  name: pod-creator    # must match the name of the Role/ClusterRole you're binding to
  apiGroup: rbac.authorization.k8s.io
```

```bash
kubectl create -f role-bind.yaml
# rolebinding.rbac.authorization.k8s.io/create-pods created

kubectl -n prod describe rolebinding create-pods
# Role: pod-creator
# Subjects: User  ballu  prod
```

## Handing the finished config off to the user
The admin's `~/.kube/config` at this point still has BOTH the `kubernetes-admin` context and the
new `ballu-context`. **Before handing this config file to ballu, strip out everything
admin-related** — keep only `ballu-context`, set it as `current-context`, and keep only ballu's
`client-certificate`/`client-key` entries under `users`. Never hand a user a config file that still
contains cluster-admin credentials.

```yaml
# What ballu's cleaned-up config should look like (relevant parts):
contexts:
- context:
    cluster: kubernetes
    namespace: prod
    user: ballu
  name: ballu-context
current-context: ballu-context   # <-- must point at ballu, not admin
users:
- name: ballu
  user:
    client-certificate: /root/ballu.crt
    client-key: /root/ballu.key
```

## Proving the scoping actually works
With ballu's config in place on the workstation:
```bash
kubectl get nodes
# Error from server (Forbidden): nodes is forbidden: User "ballu" cannot list resource "nodes"
# in API group "" at the cluster scope
```
Nodes are cluster-scoped, and ballu only has a namespace-scoped Role → correctly forbidden.

```bash
kubectl get pods -n test
# Error from server (Forbidden): ... cannot list resource "pods" ... in the namespace "test"

kubectl get pods -n default
# Error from server (Forbidden): ... cannot list resource "pods" ... in the namespace "default"

kubectl get pods            # (implicitly -n prod, from the context)
# NAME        READY   STATUS    RESTARTS   AGE
# ballupod    1/1     Running   0          20s
```
Confirms ballu can only see `prod`.

```bash
kubectl delete pod ballupod
# Error from server (Forbidden): pods "ballupod" is forbidden: User "ballu" cannot delete
# resource "pods" in API group "" in the namespace "prod"
```
Confirms the Role only granted `get, watch, list, create` — **not `delete`** — so even inside the
one namespace ballu *does* have access to, an unlisted verb is still correctly denied. This is the
whole point of RBAC: least-privilege, verb by verb, resource by resource, namespace by namespace.
